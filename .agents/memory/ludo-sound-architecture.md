## Where things live
All board-theme audio (distinct from the global UI click sounds) lives in `artifacts/ludo-dz/src/lib/sound-manager.ts`. Neon and Classic cues are synthesized live via the Web Audio API (`playSynthCue` + per-theme functions) rather than static files — zero licensing overhead, instant start, crisp at any scale. The one exception is Classic's dice roll, which plays a real recorded sample (`public/sounds/dice-roll-classic.wav`) trimmed/stretched via `playbackRate`/gain-fade to exactly match the roll animation's computed duration (`getRollDurationMs` mirrors the animation's own timing math so audio and visual can never drift apart).

## Two-layer wiring, same shape as the visual board-theme pattern
Mirrors the wiring pattern in ludo-dz-theme.md but for audio: (1) a per-theme play function exported from sound-manager.ts, (2) a call site inside GameBoardScreen.tsx gated on `isClassic`/`isNeon`/`isDz`. Both must exist for a cue to be reachable in-game — check sound-manager.ts exports AND grep GameBoardScreen.tsx for an actual call, not just one or the other.

## Capture had NO call site for any theme until the 2026-08-03 Classic pass
Unlike dice-roll and pawn-move (which already had trigger call sites for Neon and Classic), capture had zero sound wiring for any theme — only a shared visual shockwave (`setShockwave`, fires for all themes at the same spot, not theme-gated). There are two separate capture-resolution branches inside `triggerMove` (GameBoardScreen.tsx) that both need the same theme-gated sound call: the `steps.length === 0` immediate-resolve branch (piece already at destination, e.g. moving out of base on a 6), and the normal `onLastHop` callback (multi-hop moves). Wiring only one leaves captures silent on some moves but not others.

## Per-theme material identity, and a direction change worth knowing about
Neon = fully synthesized digital/sci-fi (filtered noise sweeps + oscillator tones). Classic = "wood family" built on a shared `scheduleWoodKnock` helper (filtered noise "chk" + decaying triangle "thock"), reused across click/pawn-move/capture with different amp/freq/decay per cue so all Classic cues read as one coherent material. Classic's pawn-move was originally a deliberate "polished marble" design (explicitly *not* using scheduleWoodKnock, per the old code comment) — overridden to join the wood family in the 2026-08-03 pass because the user's brief explicitly asked for "wooden pawns." If a future request revisits Classic pawn sound, wood-family (not marble/stone) is the current intended direction unless told otherwise.

## DZ sound identity status (corrected 2026-08-04 — the earlier "no isDz sound functions exist" note was stale)
DZ click (`playDzClick`) and pawn-step (`playDzPawnMove`) are wired and reachable (GameBoardScreen.tsx has real `isDz` branches at every UI click site and the pawn-hop call site) — verify with a fresh grep before assuming otherwise. DZ capture still has no `isDz` branch anywhere as of this date — that gap is real, not stale.

DZ dice roll (`playDzDiceRoll`) deliberately delegates to `playClassicDiceRoll` (2026-08-04): both themes now use the exact same cached `public/sounds/dice-roll-classic.wav` recording, gain, playback-rate, trimming, and resolve behavior. Keep the tiny DZ-specific export/call site rather than replacing it in GameBoardScreen — that preserves the per-theme hook pattern while making the intended sharing explicit. DZ click/pawn remain separate functions and should not change with dice-roll work.

The source recording is byte-identical to the user-provided `dice-rolling-on-table.wav`. Fast and Normal already share the same timing presets; Slow needs the local recorded-dice timing override to apply for *both* Classic and DZ. **Why:** DZ's ordinary Slow visual window is far longer than the sample's natural timing, whereas Classic's local override keeps the shared recorded cue natural and finish-aligned. **How to apply:** any future change to this shared sample must verify the Classic/DZ computed roll duration is identical at every speed, especially Slow, before declaring sync correct.

## "Pawn click/selection" is a distinct cue from the generic DZ click (added 2026-08-04)
Before 2026-08-04, DZ's `handlePieceClick` (the board tap that selects/moves a pawn — both the fast-path and same-cell redirect branch) played the same `playDzClick()` used by every generic UI button (settings, back, restart, speed picker). A request specifically about "pawn click/selection" means only those two `handlePieceClick` call sites, not every `isDz ? playDzClick()` site — the generic UI-button ones are a separate concern and should stay on `playDzClick`/`scheduleDzKnock` unless explicitly asked. `playDzPawnSelect` now exists as that dedicated cue, built by calling the existing `scheduleDzPlop` (pawn-move's own voice, untouched) with new tuned params rather than `scheduleDzKnock` (the generic-click family) — **why:** the brief required selection to "musically complement" the pawn-step sound, so sharing the step's exact DSP family guarantees that by construction. Select is a single hit (no secondary settle-bounce, unlike pawn-move's double-hit) so it still reads as an instant "activated" tap rather than a landing. **How to apply:** any future DZ audio request scoped to "pawn selection" or "pawn tap" means `playDzPawnSelect`'s two call sites in `handlePieceClick`, not the broader `isDz ? playDzClick()` UI-button sites — check which one the brief actually means before editing either family.

## Classic got the same select/step split, plus a from-scratch "premium" pawn family (added 2026-08-04)
Same `handlePieceClick` distinction as DZ above: a request to upgrade "pawn click/selection" for Classic means only the two `handlePieceClick` call sites, not the generic `isClassic ? playClassicClick()` UI-button sites (settings/back/restart/speed-picker), which stay on the original `scheduleWoodKnock` family untouched. `playClassicPawnSelect` is the new dedicated cue.

Unlike DZ (where only selection was new and pawn-move stayed untouched), this request asked to upgrade *both* Classic pawn-select and pawn-step together, explicitly requiring them to share the same base frequency/material. Rather than retune the old shared `scheduleWoodKnock` (still used by click and capture — retuning it in place would have changed those too), both new cues were built on a new sibling helper `scheduleClassicPawnBody` with its own dedicated noise buffer (`getClassicPawnNoiseBuffer`), so `scheduleWoodKnock`/`getWoodNoiseBuffer` and their two remaining callers (`playClassicClick`, `playClassicCapture`) are byte-for-byte unchanged. **Why:** any future "upgrade cue X but keep cue Y on the old sound" request in this file should reach for a new sibling low-level helper (own noise buffer + own schedule function) rather than editing a helper that other untouched cues still depend on — that's what makes "leave X untouched" actually safe to guarantee. **How to apply:** Classic now has two parallel synthesis families side by side: `scheduleWoodKnock` (click + capture, "plain wood knock") and `scheduleClassicPawnBody` (select + step, "premium wood/resin" — dual-oscillator triangle+sine-overtone+sine-sub over lowpass noise, no bright shimmer layer since that gold-glint motif is DZ's identity, not Classic's). If a future request touches Classic capture or click sound, `scheduleWoodKnock` is still the one they use.
