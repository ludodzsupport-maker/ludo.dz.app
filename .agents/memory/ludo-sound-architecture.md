## Where things live
All board-theme audio (distinct from the global UI click sounds) lives in `artifacts/ludo-dz/src/lib/sound-manager.ts`. Neon and Classic cues are synthesized live via the Web Audio API (`playSynthCue` + per-theme functions) rather than static files — zero licensing overhead, instant start, crisp at any scale. The one exception is Classic's dice roll, which plays a real recorded sample (`public/sounds/dice-roll-classic.wav`) trimmed/stretched via `playbackRate`/gain-fade to exactly match the roll animation's computed duration (`getRollDurationMs` mirrors the animation's own timing math so audio and visual can never drift apart).

## Two-layer wiring, same shape as the visual board-theme pattern
Mirrors the wiring pattern in ludo-dz-theme.md but for audio: (1) a per-theme play function exported from sound-manager.ts, (2) a call site inside GameBoardScreen.tsx gated on `isClassic`/`isNeon`/`isDz`. Both must exist for a cue to be reachable in-game — check sound-manager.ts exports AND grep GameBoardScreen.tsx for an actual call, not just one or the other.

## Capture had NO call site for any theme until the 2026-08-03 Classic pass
Unlike dice-roll and pawn-move (which already had trigger call sites for Neon and Classic), capture had zero sound wiring for any theme — only a shared visual shockwave (`setShockwave`, fires for all themes at the same spot, not theme-gated). There are two separate capture-resolution branches inside `triggerMove` (GameBoardScreen.tsx) that both need the same theme-gated sound call: the `steps.length === 0` immediate-resolve branch (piece already at destination, e.g. moving out of base on a 6), and the normal `onLastHop` callback (multi-hop moves). Wiring only one leaves captures silent on some moves but not others.

## Per-theme material identity, and a direction change worth knowing about
Neon = fully synthesized digital/sci-fi (filtered noise sweeps + oscillator tones). Classic = "wood family" built on a shared `scheduleWoodKnock` helper (filtered noise "chk" + decaying triangle "thock"), reused across click/pawn-move/capture with different amp/freq/decay per cue so all Classic cues read as one coherent material. Classic's pawn-move was originally a deliberate "polished marble" design (explicitly *not* using scheduleWoodKnock, per the old code comment) — overridden to join the wood family in the 2026-08-03 pass because the user's brief explicitly asked for "wooden pawns." If a future request revisits Classic pawn sound, wood-family (not marble/stone) is the current intended direction unless told otherwise.

## DZ sound identity status (corrected 2026-08-04 — the earlier "no isDz sound functions exist" note was stale)
DZ click (`playDzClick`) and pawn-step (`playDzPawnMove`) are wired and reachable (GameBoardScreen.tsx has real `isDz` branches at every UI click site and the pawn-hop call site) — verify with a fresh grep before assuming otherwise. DZ capture still has no `isDz` branch anywhere as of this date — that gap is real, not stale.

DZ dice roll (`playDzDiceRoll`) deliberately delegates to `playClassicDiceRoll` (2026-08-04): both themes now use the exact same cached `public/sounds/dice-roll-classic.wav` recording, gain, playback-rate, trimming, and resolve behavior. Keep the tiny DZ-specific export/call site rather than replacing it in GameBoardScreen — that preserves the per-theme hook pattern while making the intended sharing explicit. DZ click/pawn remain separate functions and should not change with dice-roll work.

The source recording is byte-identical to the user-provided `dice-rolling-on-table.wav`. Fast and Normal already share the same timing presets; Slow needs the local recorded-dice timing override to apply for *both* Classic and DZ. **Why:** DZ's ordinary Slow visual window is far longer than the sample's natural timing, whereas Classic's local override keeps the shared recorded cue natural and finish-aligned. **How to apply:** any future change to this shared sample must verify the Classic/DZ computed roll duration is identical at every speed, especially Slow, before declaring sync correct.

## "Pawn click/selection" is a distinct cue from the generic DZ click (added 2026-08-04)
Before 2026-08-04, DZ's `handlePieceClick` (the board tap that selects/moves a pawn — both the fast-path and same-cell redirect branch) played the same `playDzClick()` used by every generic UI button (settings, back, restart, speed picker). A request specifically about "pawn click/selection" means only those two `handlePieceClick` call sites, not every `isDz ? playDzClick()` site — the generic UI-button ones are a separate concern and should stay on `playDzClick`/`scheduleDzKnock` unless explicitly asked. `playDzPawnSelect` now exists as that dedicated cue, built by calling the existing `scheduleDzPlop` (pawn-move's own voice, untouched) with new tuned params rather than `scheduleDzKnock` (the generic-click family) — **why:** the brief required selection to "musically complement" the pawn-step sound, so sharing the step's exact DSP family guarantees that by construction. Select is a single hit (no secondary settle-bounce, unlike pawn-move's double-hit) so it still reads as an instant "activated" tap rather than a landing. **How to apply:** any future DZ audio request scoped to "pawn selection" or "pawn tap" means `playDzPawnSelect`'s two call sites in `handlePieceClick`, not the broader `isDz ? playDzClick()` UI-button sites — check which one the brief actually means before editing either family.

## Classic got the same select/step split, on a sibling helper kept apart from click/capture (added 2026-08-04)
Same `handlePieceClick` distinction as DZ above: a request to upgrade "pawn click/selection" for Classic means only the two `handlePieceClick` call sites, not the generic `isClassic ? playClassicClick()` UI-button sites (settings/back/restart/speed-picker), which stay on the original `scheduleWoodKnock` family untouched. `playClassicPawnSelect` is the dedicated select cue; `playClassicPawnMove` is the step cue.

Both were asked to share the same base frequency/material, so rather than retune the old shared `scheduleWoodKnock` (still used by click and capture — retuning it in place would have changed those too), they were built on a sibling helper `scheduleClassicPawnBody` with its own dedicated noise buffer (`getClassicPawnNoiseBuffer`), leaving `scheduleWoodKnock`/`getWoodNoiseBuffer` and their two remaining callers (`playClassicClick`, `playClassicCapture`) byte-for-byte unchanged. **Why:** any future "upgrade cue X but keep cue Y on the old sound" request in this file should reach for a new sibling low-level helper (own noise buffer + own schedule function) rather than editing a helper other untouched cues still depend on — that's what makes "leave X untouched" actually safe to guarantee. **How to apply:** Classic has two parallel synthesis families side by side: `scheduleWoodKnock` (click + capture) and `scheduleClassicPawnBody` (select + step, material below). If a future request touches Classic capture or click sound, `scheduleWoodKnock` is still the one it uses.

## Per-theme welcome jingle on Board-screen entry (added 2026-08-04)
Each theme now has a one-shot `play<Theme>WelcomeJingle()` (~1.5-1.9s), fired from a single mount-only `useEffect` (empty deps) in `GameBoardScreen.tsx` — a screen-entry cue, not a per-move cue, so it belongs with the BGM pause/resume lifecycle (see `ludo-bgm-system.md`) rather than the click/pawn/dice trigger-site pattern above. Gated on `soundEnabled` (SFX) automatically via `playSynthCue`, fully independent of BGM. **Why it needed brand-new low-level helpers per theme** (`scheduleMarimbaNote`, `scheduleDzChimeNote`, `scheduleNeonChimeNote`) rather than reusing `scheduleWoodKnock`/`scheduleClassicPawnBody`/`scheduleDzKnock`/`scheduleDzPlop`/neon's inline cues: a melodic multi-note jingle needs a longer, tonal, ringing envelope that those short contact/percussive envelopes were never tuned for — same "don't retune a helper other cues depend on" principle as the Classic pawn split above. Per-theme melodic identity chosen to extend each theme's established material rather than invent a new one: Classic = marimba (sine fundamental + ~3.93x fast-decaying overtone, mallet noise chiff) playing a "do-mi-sol" bugle fanfare; DZ = bright struck-metal/finger-cymbal chime (triangle fundamental + fifth overtone + inharmonic ~3x "ting", landing note gets the family's gold-glint shimmer) playing a Hijaz-tetrachord run (root/♭2/♯2.../P4 — the half-step/augmented-second/half-step pattern read as "oriental" without going microtonal); Neon = sawtooth power-up sweep + triangle arpeggio in stacked perfect fourths + `getNeonNoiseBuffer` glint bursts (same technique as the dice roll's Layer 2) + a bright sine "system ready" ping. **How to apply:** a future "add/change a per-theme intro/outro/transition jingle" request should follow this same shape — new sibling helper(s) per theme, one mount-effect trigger site, gated through `playSynthCue` for the SFX toggle — not a retune of any existing per-move cue's helper.

## Classic pawn material direction reversed same-day: wood/resin → dry marble/stone (2026-08-04)
The first `scheduleClassicPawnBody` design (dual detuned oscillators — a fifth-above overtone plus an octave-below sub-bass layer — over lowpass-filtered noise, with a second hit ~30ms later as a "settle bounce" for the step cue) was rejected in the same session as sounding reverby, echoey, and hollow, even though it used no delay/convolution node at all. The perceived "reverb/echo/hollow" came entirely from synthesis choices: a sub-bass layer (reads as hollow low-end/boom), a genuinely delayed second hit (literally is an echo, whatever it's called in the code), a lowpass noise filter (dulls the transient), and decay times in the 70-115ms range (long enough to read as a tail on a cue that should feel instant). It was replaced with a single-hit-only design: bandpass (not lowpass) noise tuned high for a bright hard transient, no sub-bass layer at all, and decay capped well under 70ms even at the slowest hop speed. **Why:** for a "dry/punchy/instant" brief, the danger signs are sub-bass layers, any secondary/delayed hit, lowpass-filtered noise, and >70ms decays — avoid all four regardless of how the request phrases "no reverb," since none of them are literal reverb nodes but all four read as one perceptually. **How to apply:** wood/resin (warm, lowpass, sub-heavy) and marble/stone (bright, bandpass, single-hit, no sub) are now known opposite poles for this pawn family — check which one the current brief actually wants before reusing either recipe, and default to the marble/stone design (current as of this date) unless told otherwise.

## Normal theme (added 2026-08-31): shared recorded dice + original cartoon piece cues
As of this date the Normal board's piece sounds were redesigned and its dice joined the shared recording, per a brief asking for "cartoonish, lively" piece SFX and "reuse the existing dice sound, no new dice sound."

**Dice — Normal delegates to the shared sample.** `playNormalDiceRoll` now just calls `playClassicDiceRoll` (same pattern DZ already used), so Normal/Classic/DZ/Neon all play `sounds/dice-roll-classic.wav`. Consequence that must not be regressed: Normal had to join the slow-end timing override, so the condition in `GameBoardScreen.tsx` `handleRoll` is now `(isClassic || isDz || isNormal) && diceSpeed <= CLASSIC_SLOW_DICE_MAX_SPEED ? CLASSIC_SLOW_DICE_TIMING : diceTiming`. **Why:** Normal's ordinary `diceTiming` slow window runs up to 3590 ms at slider 0, which would stretch the 1.109 s take to ~0.31× and read as a slow-motion rumble; with the override Normal's computed roll duration is byte-identical to Classic's and DZ's at every slider (1708 ms below slider 10, `diceTiming` above). This is a Normal-only change (guarded) and only affects Normal's dice *visual* window at slider ≤ 10 — verified the durations match Classic/DZ exactly.

**Piece cues — original synthesized cartoon designs, Normal-only.** `playNormalPawnMove` = a springy "boing" (`scheduleNormalBoing`: upward "pop" sweep + triangle body with a rising-then-falling hop arc + decaying audio-rate FM twang at ratio 2.76 + decaying 34→21 Hz vibrato) plus a quieter settle bounce ~72 ms later (`depth:0.5, tail:0.5`). `playNormalCapture` = a three-beat "gotcha": bonk (300→126 Hz sine glide) + gulp (190→640→155 Hz glide sweeping through a ~620–920 Hz resonant bandpass with a parallel dry path, plus a ×2.02 throat partial) + a quiet "ding" (1568 Hz + 2.42× inharmonic partial). Both use `getNormalNoiseBuffer` only; none of the shared helpers (`scheduleWoodKnock`, `scheduleClassicPawnBody`, `scheduleDzPlop`, `scheduleDzKnock`) are used, so other themes are untouched. Capture is wired at BOTH call sites in `GameBoardScreen.tsx` (`steps.length===0` and `onLastHop`) via `else if (isNormal) playNormalCapture()`, matching the established two-site capture pattern.

**Tuning lesson (measured, not guessed):** a narrow, pitch-chasing formant (Q≈5.5) starves the fundamental by ~28 dB and the whole gulp disappears under the bonk. Fix: a gentler band (Q≈2) that the pitch sweeps *through* + a parallel dry path. Keep this in mind if the gulp is ever reported "too quiet" — the instinct to raise Q or make the band chase the pitch will make it worse.

**Verification tooling (not committed; lives in /tmp, ephemeral):** a headless-Chromium `OfflineAudioContext` harness (`puppeteer` + `@sparticuz/chromium` from npm) renders the REAL exported cue functions (the module is bundled with esbuild and tricked into using an OfflineAudioContext by reporting `state === "running"`), then writes listenable WAVs + log-frequency spectrograms. This lets us measure level parity (hop ≈ −10.4 dB vs Classic −11 / DZ −7.5; capture ≈ −8.8 dB vs Classic −8.5), confirm no clipping and no energy > 6 kHz (no harshness), confirm the hop decays to −85 dB by the next hop (no smear), and visually confirm the boing/gulp pitch contours. **Why this matters:** for any future sound request, do NOT ship a cue that was only hand-tuned by reading code — render and measure it offline first, and keep the rendered WAV/spectrogram in `artifacts/ludo-dz/sound-preview/` (gitignored, not shipped) for the user to audition.
